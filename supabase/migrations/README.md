# Migration naming convention

Every new migration file in this directory should be named `YYYYMMDD_short_description.sql` (e.g. `20260730_tighten_brands_update_policy.sql`) — a plain calendar date, not a full timestamp, followed by a lowercase snake_case description of what the migration does; if more than one migration lands on the same date, disambiguate with a `-2`, `-3`, ... suffix on the date (`20260730-2_fix_brands_guard_search_path.sql`) rather than reusing a bare date twice. This directory started empty: the project's first ~47 migrations were applied directly to the live database (via the Supabase dashboard/SQL editor and the `apply_migration` MCP tool) and are tracked only in the project's own remote migration history, not as local files — they are intentionally not being renamed or backfilled here, since rewriting history that's already applied is exactly what this convention is meant to avoid; it governs new migrations from this point forward only. For the current end state of the whole schema in one file (rather than replaying history), see `supabase/schema.sql`; for the pre-existing narrative/annotated history of *why* things are the way they are, see `supabase/migrations.sql`.
